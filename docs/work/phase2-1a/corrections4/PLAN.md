Wall-clock names order the other candidates, never decide whether the current protected original survives. No new backup manifest, storage migration, KDBX metadata or cryptography. A post-commit failure is a distinct typed `BackupRetention` warning, never an unsaved/retryable deletion result. Preserve BackupRefresh/BackupPrune/Journal classifications, native origin/ID retention and CLI warning semantics.

### R4-02: native-issued opening reservation and owned invalidation

- Introduce a native-generated UUID **session owner**, separate from vault/entry identity, policy Ticket and frontend generation. It contains no path/name/value. Native owns it under the same gate as Opening/Active/Locked transitions. No UUID reuse across reservations; no persisted metadata or authorization-by-ID claim.
- IPC: `vault_prepare_open() -> string` atomically starts native Opening, closes/discards the prior session, and returns the new owner ID **before any password is sent**. Existing `vault_unlock`/`vault_create` take required `sessionId` and consume only that still-current Opening reservation; they must not call begin_open again. Stale, cancelled, expired, duplicate or foreign reservations cannot install protected state. Serialize KDFs as before. Native failures preserve actionable current authentication errors.
- All status-producing command replies include `sessionId: string | null`; unlocked status must carry the active native owner checked against the completed policy ticket. Locked status carries null. Upgrade/reload retain the current owner. Stamp and postcheck on the actual native boundary, not from a vault filename or frontend guess.
- `vault-locked` payload becomes `{sessionId: string}`, identifying the **invalidated** Opening/Active owner, captured under the gate before removal/replacement. OS lock/suspend/idle/manual lock/poison/open replacement/exit route through this ownership rule. The old owner's notice cannot name a replacement reservation. A failed opening retires its owner without a second event that erases its terminal error.
- `vault_lock` accepts the expected nullable `sessionId` and refuses to lock another owner. OS/exit native lock remains unconditional and authoritative. A delayed A command as well as an A notification cannot lock B. Null acknowledges only an already unowned/locked state, not an arbitrary active B.
- Frontend/API begins an opening transition synchronously, fences prior replies and marks its current native owner unknown before requesting the reservation. A presentation-only opening event fences App requests/transitions and clears an old protected view **without unmounting the already-locked Unlock form that initiated this request**. All existing ordinary success/error generation fences and known-commit receipts remain.
- The API adopts only a still-live reservation and then dispatches credentials with that ID. Track fixed invalidated native IDs independently of React roots so a genuine B lock arriving before its reservation/status reply cannot be lost. No credentials after an already-invalidated reservation. Protected status from an invalidated ID is rejected/sanitized. Current authentication errors remain actionable. Never forward obsolete metadata.
- App handles native notices through this identity boundary. Matching current Opening/Active owner closes protected UI promptly; older/duplicate A events do not remount/erase B or its newer error. Unknown-owner bootstrap notices retain tombstones until corresponding replies are checked. Missing/malformed event identity fails closed with an explicit unconfirmed-lock error and an owned native lock attempt, not a silent claimed lock over an active vault. No blanket ignore-while-opening or timer-based event suppression.
- Permanent actual App/API/Unlock regressions enumerate old A events before/after B reservation ACK, during B KDF/before its reply, after B opens, duplicates and between/after roots; genuine B locks at all these boundaries, current status/lock/errors, expired/resubmitted reservations, malformed events and large policy tickets without JS-number identity. Native tests assert the emitted invalidated owner and actual policy state. No actual OS lock/suspend is used.

### R4-03: immediate cleanup result is an explicit part of copy outcome

- Keep ClipboardLease's immediate partial-publication cleanup, sequence/text ownership, expired retry and newer-user-copy protections. Do not postpone immediate cleanup just to simplify warning accounting.
- Add a typed internal copy result/failure that carries the original publication error plus optional `{lease_generation, cleanup_error}` from the immediate cleanup attempt; it must contain no clipboard value/OS sequence. Session accounts for that result with the **same** episode handler used by clear/tick, then returns the original publication error to the caller. Legacy leaf tests can use a compatibility wrapper if it delegates to the same typed implementation; production Session must use the reporting variant.

Successful not-due ticks are not recovery. Explicit Session.warn occurrences remain separate.
