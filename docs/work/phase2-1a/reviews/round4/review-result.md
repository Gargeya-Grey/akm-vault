### 1A-R4-01. P2. A dated pre-deletion backup can be pruned immediately while the UI says it was retained

**Classification:** reproduced with the exact release CLI and fake vault; the GUI consequence is supported by source inspection, not an independently launched GUI.

**Locations:** `crates/akm-core/src/vault.rs:512-525,548-565,596-627`; `desktop/src/components/KeysView.tsx:113-116,339-345`; `desktop/src/App.tsx:16-20`; CLI warning formatting at `crates/akm-cli/src/main.rs:342-344,485-488`.

The commit creates a verified dated copy of the original, then `prune_backups` sorts backup names by their wall-clock timestamp and removes the oldest names. It does not protect the copy just made. If five existing dated backups sort later than the current clock, the newly created original sorts first and is pruned. If `.bak` refresh also fails, no copy of the immediately preceding vault need remain. The delete success message nevertheless says the previous vault was retained as a dated encrypted backup. The fixed `backupRefresh` notice and CLI warning also say a retained backup exists. No prune error is raised when this removal succeeds.

The independent probe created a fake vault with one fake key. It installed five valid, earlier empty-vault backups with future-dated names to model clock skew, made only the scratch `.bak` path a directory to inject refresh failure, and deleted the key using the exact pinned CLI. The deletion returned exit 0 and printed `vault saved with a retained backup`. All five surviving dated files had the earlier empty-vault hash, not the pre-deletion vault hash. A separate CLI read of the current vault and all five surviving encrypted backups showed the deleted fake key absent from each. This demonstrates the combination with fake data only. It does not establish that an owner's vault has lost data.

Evidence: `probe_backup_clock_skew.py`, `probe_backup_clock_skew.log`, `probe_backup_validate.py`, and `probe_backup_validate.log` in this review's scratch directory. The tested CLI hash is `0024f9005a68bf5b5ab9d32297c9d6eb4043ee5616a7ae6c465a054adfddcdc0`. The pruning behavior predates this cycle, but the changed delete and typed-warning copy are direct callers that promise the very backup the pruning step can remove. Therefore the earlier R2-05 wording seam does not fully meet the frozen truthful-backup contract.

**Correction and acceptance test:** protect and verify the particular pre-commit encrypted original through pruning, including a clock rollback or future-named backups. Preserve the five-backup policy and the post-commit warning/non-retryable result. If retention cannot be established, do not say it was retained. Test actual CLI and native/UI warning callers with five later-sorting valid backups plus a failed `.bak` refresh. Verify that the exact pre-deletion contents remain recoverable, that the deletion remains a success, and that warning wording matches the actual result.

### 1A-R4-02. P2. An unowned delayed native lock event can hide an active B

**Classification:** reproduced through the actual frozen `App`, `api`, and `Unlock` code with mocked native IPC and a deliberately delayed event. Native WebView2 timing was not independently reproduced.

**Locations:** `desktop/src/App.tsx:58-69,137-143,169-179,273-283`; `desktop/src-tauri/src/lib.rs:24-29`; `desktop/src-tauri/src/session.rs:173-176,194-201,260-269`; `desktop/src-tauri/src/policy.rs:39-58,74-80`.

Clicking Lock immediately calls `showLocked`, before the native `vault_lock` reply. The native lock callback emits `vault-locked` with `()` and no origin ticket. App's listener calls `showLocked` for every delivery, without checking which native session the event belongs to. If A's already-emitted lock notification reaches JavaScript after B starts opening or after B opens, it advances the frontend generation and either rejects B's successful unlock response or hides B's already-open view. The old notification does not lock B in native state. The screen can therefore appear locked while the new native session remains active. This is separate from, and not a claim that, a retained completion receipt false-locks B.

Two independent scratch tests passed by asserting the current failure behavior. One delivers A's queued lock notification after a mocked successful B open. The other delivers it after B becomes native-active but before B's unlock reply reaches the App. In both cases the actual App shows the unlock screen while the mock still records B as active. The test supplies the event ordering; it is not an actual Windows lock or proof of a real WebView2 timing occurrence. The pinned Tauri source makes this a supported asynchronous concern rather than a synchronous-callback assumption: `tauri-2.12.5/src/webview/mod.rs:2230-2236` emits to `eval`, and `tauri-runtime-wry-2.12.3/src/lib.rs:1739-1745` queues `EvaluateScript`. These lines do not by themselves prove a specific real-world ordering.

Evidence: `frontend-probe/src/probe-stale-native-event.test.tsx`, `frontend-probe/vitest.config.ts`, and `frontend-probe/probe-stale-native-event-final.log`. The two passing tests are defect-observation tests, not acceptance tests for the desired behavior.

**Correction and acceptance test:** carry a native lock/session identity or use another race-safe reconciliation protocol so an old notification cannot invalidate B. Do not simply ignore notifications while opening, since a genuine current lock must still close protected state promptly. Test both old-event deliveries above, current lock during opening, current lock after B opens, native state, and ordinary reply fencing. Obtain a safe native-boundary proof of the relevant ordering separately if authorized.

### 1A-R4-03. P3. Partial-copy cleanup bypasses the episode handler

**Classification:** reproduced with the frozen actual `Session`, `ClipboardLease`, and policy source and a fake clipboard backend. No real clipboard was opened or changed.

**Locations:** `desktop/src-tauri/src/clipboard.rs:45-75,320-340`; `desktop/src-tauri/src/session.rs:437-447,570-585`; episode contract in frozen `docs/work/phase2-1a/corrections3/PLAN.md:29-36`.

After a partially failed publication, `ClipboardLease::copy` installs a lease and calls `self.clear()` immediately. It discards a cleanup error and returns only the original publication error. `Session::copy` propagates that error directly and never passes the failed immediate cleanup through `cleanup_clipboard`. If the next due tick succeeds, the episode ends without ever allocating a warning ID. The local copy error is not the retained app-global cleanup warning promised by the contract and may disappear when its view is hidden or left.

The scratch Rust probe used a fake backend that reports a partial publication and refuses its first clear while leaving a fake value in its own in-memory buffer. The actual Session returned the fake publication error, held the fake value after the failed cleanup, and reported zero application warnings. The next tick succeeded and the warning count stayed zero. A second case first created and recovered from one recorded cleanup episode without acknowledging it, then caused the partial-publication cleanup failure and recovery for a new lease. There was still only the first warning ID. Acknowledging that old ID left no warning for the second episode. The probe places the policy in an active fake session directly and uses no real vault or clipboard; it links existing debug dependencies but compiles the pinned session and clipboard source copied from the reviewed archive.

Evidence: `probe_partial_cleanup.rs`, `run_probe_partial_cleanup.py`, `probe_partial_cleanup-build-final.log`, and `probe_partial_cleanup-final.log`.

**Correction and acceptance test:** route the result of this immediate owned-lease cleanup through the same episode accounting without changing sequence/text ownership, partial-publication cleanup, or a newer user's clipboard. Inject partial publication, failed immediate clear, successful next tick, and a second such episode while an earlier ID is pending. Assert a distinct retained ID for each failure episode, no unbounded IDs for retries, and dismissal of only the observed ID. Retain the existing partial-publication and newer-identical-copy regressions.
