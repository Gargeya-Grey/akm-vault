## Ranked findings

1. **P1: A selected `PROMPT` secret is printed when the terminal opens.** `desktop/src-tauri/src/launch.rs:216` injects every non-reserved selected name. `PROMPT` passes the core name and reserved-name checks, but `cmd.exe` uses its value as the visible command prompt. A key named `PROMPT` therefore appears on screen immediately, despite the confirmation saying secret values are not shown. **Reproduced:** a windowless `cmd.exe /d /q` with a fake `PROMPT` printed the fake value. **Closing test:** use a fake vault containing `PROMPT`, exercise the launch boundary, and assert that it is refused before confirmation or otherwise cannot be displayed by the child.

2. **P2: `cmd.exe` can run AutoRun code with the keys before the user types anything.** `desktop/src-tauri/src/launch.rs:153` starts `cmd.exe` without `/d`. A configured Command Processor AutoRun command receives the injected environment and runs automatically. The review warns about programs the user starts, but does not disclose this automatic recipient. Microsoft documents `/d` as disabling these commands. The real-child test adds `/d`, so it cannot catch the production behavior. **Found by inspection.** **Closing test:** run a windowless fake-key child with a controlled AutoRun fixture and prove the production command does not execute it; also check the warning against the actual launch behavior. Microsoft `cmd` documentation: https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd

3. **P2: The child also receives unrelated parent environment secrets.** `desktop/src-tauri/src/launch.rs:208` inherits the whole AKM process environment except `AKM_*`, then adds the selected keys. If AKM was started with an unrelated `AWS_SECRET_ACCESS_KEY`, for example, that value reaches the terminal and its descendants although the review lists only the selected vault names. The warning does not say this. The chosen working folder also participates in command lookup, so a program in an untrusted folder can receive those variables when invoked by name. **Found by inspection.** **Closing test:** launch a windowless fake child with an unrelated fake parent secret and assert the chosen environment policy and review warning explicitly account for it.

4. **P2: Untrusted scope text can impersonate the native review.** `desktop/src-tauri/src/launch.rs:71` interpolates project and environment verbatim. They can contain embedded newlines, quotes and control or directional characters. A matching vault project such as `demo"\nFolder: C:\trusted` can insert apparent review lines and mislead the person approving the disclosure. Variable names have stricter validation, but scope names do not. The review test uses only ordinary text. **Found by inspection.** **Closing test:** use fake vault scopes with newlines, bidi controls and long strings; assert the native review displays unambiguous escaped or rejected values and retains the real folder, names and warning.

5. **P2: A lock can occur between the last check and display of the review.** `desktop/src-tauri/src/launch.rs:336` checks the ticket after the picker, releases the gate, and later calls `confirm`. A lock in that gap can be followed by a native dialog showing the old project, environment and variable names. The later check prevents the terminal start, but does not prevent the stale review from appearing. This is fault class A. The picker test locks *inside* the picker, before the check, and misses this gap. **Found by inspection.** **Closing test:** place a barrier after `ensure` and before dialog presentation, lock the session, and assert that no old-session review is presented.

6. **P2: Journal and secret reads can continue after the session locks.** `desktop/src-tauri/src/launch.rs:352` enters `access_reviewed`, whose initial gate check ends before its closure runs. A lock can then complete while the vault mutex remains held. The closure can append `run-requested` and read values after that lock; only the subsequent `while_current` prevents the child from starting. This is a class A state change after the session was retired. The design’s assertion that the check and act remain one step is therefore incorrect for the journal and read. **Found by inspection.** **Closing test:** block immediately after the access check, complete a lock, resume, and assert that neither a journal append nor a secret read occurs.

7. **P2: The launch violates contract 11’s vault-release requirement.** The vault remains in `Session` and its mutex is held across the child start (`desktop/src-tauri/src/launch.rs:363`). Contract 11 requires release before starting a child. The design note correctly identifies the conflict, but does not amend the contract. This regresses the release portion of earlier finding **C1**. **Found by inspection.** **Closing test:** verify at the real launch boundary that the vault is released before process creation, or obtain and record an owner decision that changes the contract, followed by a test of the newly approved contract.

8. **P2: Arbitrary KDBX field names can disclose sensitive text through history.** `desktop/src-tauri/src/commands.rs:481` forwards every changed field name from the core. Foreign KDBX custom field names are arbitrary strings and can themselves contain sensitive text. They reach IPC and the drawer (`desktop/src/components/KeyDetail.tsx:33`), even though values are not serialized. The existing test checks password values in ordinary fields, not sensitive custom names. **Found by inspection.** **Closing test:** import a fake foreign history with a fake secret in a changed custom field name and assert it reaches neither IPC nor the UI, while safe known field categories remain useful.

9. **P2: A successful launch can lose its completion when only the view expires.** `desktop/src/components/UseKeys.tsx:73` invalidates the component’s request on hide or view expiry. If the native review is then approved and the same session remains current, `desktop/src/api.ts:39` creates no launch outcome, and `reportCompletion` is not called. The component drops the successful reply, leaving no retained indication that a key-bearing terminal exists. The component test explicitly expects the late message to disappear but does not check a retained outcome. **Found by inspection.** **Closing test:** dispatch a launch, expire the view without changing session, approve it and deliver success; assert a session-owned, secret-free completion remains available without allowing an old session to invalidate a newer one.

10. **P2: The disclosure button is the default in the native confirmation.** `desktop/src-tauri/src/launch.rs:143` puts “Open terminal” first. The pinned dialog implementation sets `nDefaultButton` to zero, for which Windows selects the first button. An unintended Enter, including one carried over from the picker interaction, can approve the key-bearing process without an affirmative selection of that action. The plugin’s lack of a default-button option does not make this a safe default. **Found by inspection; the real dialog was not opened.** **Closing test:** verify the native dialog initially defaults to Cancel and that Enter at presentation does not start a fake-key terminal. Real-window confirmation remains owner-gated. Microsoft task-dialog documentation: https://learn.microsoft.com/en-us/windows/win32/api/commctrl/ns-commctrl-taskdialogconfig

11. **P3: The claimed “journal before any value is read” property and its test are false.** `desktop/src-tauri/src/launch.rs:325` calls `plan_env` before either dialog, and that function calls `stored_secret` to validate each selected value. It does so again before `disclose_env`. The journal-failure test proves no child starts; it does not observe secret reads. This is an internal plaintext read, not evidence that a value reached the page or child before the journal. **Found by inspection.** **Closing test:** instrument secret reads and fail the journal append; assert the intended ordering, or correct the documented promise and test name if that ordering is deliberately changed.

12. **P3: Zeroizing `LaunchSecrets` does not clear all parent-process copies.** `desktop/src-tauri/src/launch.rs:216` copies values into `Command`; dropping that command does not establish that its buffers are zeroed. The CLI’s `child.rs` has the same limitation. The new wrapper reduces one copy’s lifetime but does not prove the launch’s values are cleared from AKM memory. **Found by inspection.** **Closing test:** use an injectable process builder or equivalent instrumented buffer to verify cleanup on both spawn success and failure, and state any unavoidable platform copies.

## Verdicts

**Source acceptance: NO.** This review fails under the pass rule because it establishes P1 and P2 findings. C1’s vault-release requirement was checked and is violated. The earlier phase-two findings and the UI rebuild fixes are outside this work unit; I did not independently accept their fixes.

**Work unit complete: NO.** In addition to the source findings, the real picker, confirmation, console and owner-present proofs remain unrun.

The native history read does use the session and presentation fences, and its page state clears on hide or native view expiry. The raw custom field names are the exception described above. The launch binds its plan to the session and vault revision, and the final process start runs under the session gate. I did not find a vault-mutex/session-gate deadlock in the inspected paths: lock releases the gate before its nonblocking vault discard. This is an inspection result, not a concurrency proof.

The journal failure path does prevent the child from starting, preserving contract 12’s fail-closed launch behavior. It does not provide the stronger claimed guarantee that no value was read before the record.
