DESIGN: NO

1. **Blocking. A lock can wait for an earlier cleanup.** Section 2.3 moves the notice ahead of the cleanup initiated by `locked_gate`, but `Session::tick` (`desktop/src-tauri/src/session.rs:268`) performs cleanup while holding the same gate that `lock()` must acquire. If a tick is stalled inside cleanup, a concurrent lock cannot send its notice until that cleanup returns. The recorded exception permits waiting for an in-progress copy; it does not cover an in-progress cleanup. Move cleanup outside the session gate, with an ownership and concurrency fence, so lock can send its notice without waiting for another cleanup. Add a fake barrier test that holds a tick cleanup and checks that the lock notice arrives before the barrier is released.

2. **Blocking. The attempt budget and notice order miss session paths.** Section 2.3 relies on `gate()` reporting whether it already performed cleanup. That does not cover another `gate()` call within the same public call. For example, `tick()` can attempt a due cleanup just before idle expiry, then `discard_locked_vault` (`desktop/src-tauri/src/session.rs:249`) can call `gate()` after the clock crosses the deadline and trigger a second attempt. Also, `start_open` (`desktop/src-tauri/src/session.rs:314`) calls cleanup before retiring the old owner even when entry did not expire. `current()` and `opening()` can independently expire the policy, and app exit events (`desktop/src-tauri/src/lib.rs:82`) are absent from the inventory. Carry one attempt budget through the whole entry call, including nested gates and expiry checks; retire the old owner before `start_open` cleanup; inventory and test those paths, including `lock_owned` and `activity`.

3. **Blocking. W1 and W2 omit a documented clipboard exception.** Section 0 (`docs/design/unit1a-repair.md:19`) omits Microsoft's qualification that a delayed-rendered change does not increment the sequence until rendering. It also says no other program can change the clipboard while AKM has it open. A clipboard owner responding to `WM_RENDERFORMAT` can call `SetClipboardData` while the requesting application holds it open. See [GetClipboardSequenceNumber](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber) and [WM_RENDERFORMAT](https://learn.microsoft.com/en-us/windows/win32/dataxchg/wm-renderformat). The existing clear path (`desktop/src-tauri/src/clipboard.rs:439`) checks the sequence before reading text and does not check it again before emptying. The cited facts therefore do not establish the note's general ownership claim or its contract 10 proof. W3 also treats the owner as destroyed, although `Owner::drop` (`desktop/src-tauri/src/clipboard.rs:459`) ignores `DestroyWindow`'s result. State these limits, fence or reject an unexpected owner or sequence change around the read, and test delayed rendering and owner-destruction failure with the fake API. An actual Windows erasure was **not reproduced**.

4. **Blocking. The CLI capability does not close the disclosure class.** Section 2.5 bans `.secret` reads outside `disclose.rs`, but `Vault::env_vars` (`crates/akm-core/src/vault.rs:404`) returns secret-bearing strings without a `.secret` access in the CLI caller. The existing run and export paths (`crates/akm-cli/src/main.rs:391`) call it before the request record. A future caller can write those returned strings directly and pass the proposed structural test. `ApiKey` also implements `Serialize` and `Debug` and has a public secret field (`crates/akm-core/src/model.rs:31`), so serializing a whole key is another bypass. Keep raw vault and key access inside the disclosure boundary, provide a batch authorization for scoped export and run, and bind each capability to its required journal action. Add negative tests for the `env_vars` and whole-key serialization bypasses, plus failed-journal tests at each sink.

5. **Blocking. Rust permits the defining module and its descendants to access a private item, so code in that scope can construct `Publication(Outcome::Untouched(error))` after an empty. The proposed mutant can therefore compile despite the moved tokens. See the [Rust visibility rules](https://doc.rust-lang.org/reference/visibility-and-privacy.html).
