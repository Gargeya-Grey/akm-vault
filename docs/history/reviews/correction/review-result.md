# Read-only correction review

Historical result against the original pinned revision. See `followup-review-result.md` for the current follow-up after subsequent source corrections and real clipboard evidence.

Code verdict: not approved. The original committed-outcome race and export security-gate blockage are corrected, but supported ownership and UI lifecycle defects remain. Phase-1 verification is also still open.

## Ranked findings

1. **P2, medium. Desktop export still claims temporary filenames instead of owned files.** `desktop/src-tauri/src/private_export.rs:172-195,217-229`. Preparation closes the file and retains only its pathname. A process able to rename that file can move it and replace its former name before authorization/publication. The actual Windows helper probe reproduced both outcomes. Cancellation deleted the unrelated replacement and retained the renamed plaintext. Publication reported success but exported the unrelated replacement, again retaining the owned plaintext. The corrected CLI survives this identical interleaving. Keep the owned file handle through preparation and use handle-based publication/deletion, disarming cleanup after publication. Add the CLI's renamed/replaced-temp regression to desktop export. This is a reproducible file-ownership failure, not a claim that an in-flight authorized filesystem syscall can be cancelled.

2. **P2, medium. Failed unlocks lose their explanation because their own lock event destroys the requester.** `desktop/src-tauri/src/session.rs:299-305`; `desktop/src/App.tsx:30-41,199-203`; `desktop/src/components/Unlock.tsx:24,89-92`. A real wrong-password `Session::open` emitted one lock notification before returning its `open` error in the native probe. The corresponding frontend interleaving rekeys/unmounts Unlock, then drops the rejected request's error. The user gets a cleared form without the password/file error. The same native branch handles failed creation. Avoid emitting an additional lock transition for an opening failure when no protected view was installed, or correlate that terminal error to a surviving locked parent. Independent lock events must still invalidate stale work. The focused component test fails.

3. **P2, medium. An initial status rejection after lock strands startup permanently.** `desktop/src/App.tsx:36,49-65,181-198`. A lock while initial status is pending leaves `status` null and invalidates the request. If that request rejects, its catch does nothing. No polling starts and neither an unlock form nor a retry button exists. The deferred-rejection component probe ends at "Opening the vault..." with no recovery action. Start a fresh fenced status request after boot invalidation, or preserve a generic retryable boot state without accepting obsolete protected data.

4. **P3, low. Hiding invalidates export previews but not import reviews.** `desktop/src/components/Settings.tsx:66-69,230-234`. The visibility handler calls only `hidePreview`. A pending import response can therefore install its old token/review after hide and reappearance, contrary to `PHASE1.md:95`. The focused test fails. Invalidate pending import-preview generations and clear the review on hide. Treat already-dispatched confirmations separately so their side-effect acknowledgments are not discarded. This is not a recurrence of the fixed prod-token/dev-label mismatch.

5. **P3, low. CLI documentation claims nonexistent Unix export permissions.** `crates/akm-cli/README.md:42-45` says Unix exports use mode 0600. The non-Windows implementations in `crates/akm-cli/src/export.rs:132-144,217-222,479-484` instead reject private file exports. Document Windows-only file export, or restore and test the Unix implementation. Do not leave an unsupported protection claim.

## Six-correction verdict

- **1. Committed outcomes appear corrected.** Independent fake-vault probes confirmed add/update/remove/import/create/upgrade persist exactly once and produce a secret-free `completedWhileLocked` outcome after locking. Native `finish`/`check_completed`, command callers, and the frontend mutation wrapper preserve the distinction. Read/reveal guards suppress obsolete plaintext. Export cancellation/publication probes preserve the intended cancellation boundary and completed receipt.
- **2. Stale successful replies appear fenced** for unlock/create, reload/upgrade and polling, with parent and child guards. The error paths in findings 2 and 3 prevent full acceptance.
- **3. Scope snapshots and token binding appear corrected.** Export edits, import edits/cancel, and unmount generations reject stale responses. Import hiding remains incomplete as finding 4 describes.
- **4. Export preparation and bulk I/O no longer hold the security gate.** Authorization immediately before publication is the boundary. An ordinary preauthorization cancellation removed its temp in the probe. Authorized publication after lock returned a completed receipt. Finding 1 exposes the adjacent ownership weakness.
- **5. Clipboard code now installs exclusions before text, samples sequence under the same open interval, transfers movable allocations only on successful publication, and retains partial-failure leases.** Owner lifetime includes CloseClipboard. No additional definite code defect is established, but sequence validity after close/owner destruction and actual cleanup remain runtime-unverified. Fake API tests cannot prove these Windows semantics.
- **6. CLI export appears corrected.** Per-handle capability and protected-DACL checks precede plaintext writing. Handle-owned cleanup/publication and no-overwrite behavior address the original failure modes. The identity-swap probe passed for CLI and failed for desktop. Real disk-exhaustion behavior remains unverified.

No additional supported regression was found in core decrypted read-back/content comparison, native UUID targeting, retained backups, explicit upgrade/KDF preservation or journal append serialization. This is a source/probe conclusion, not a claim that integration was audited.
