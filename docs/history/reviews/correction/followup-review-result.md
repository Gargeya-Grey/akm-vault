## Supported current finding

**P2, medium. A late completed receipt false-locks a newer session and prevents recovery.**

`desktop/src/App.tsx:45-49`; `desktop/src/api.ts:24-26`; `desktop/src/sessionBoundary.ts:13-15`; `desktop/src-tauri/src/session.rs:232-243`.

An authorized session-A export may finish after A was locked and session B successfully opened. Native correctly returns completedWhileLocked for A and leaves B active. However, the uncorrelated frontend completion event calls showLocked on B without a native lock. The user sees a locked form while the backend remains active. The next unlock calls begin_open over active B, which emits vault-locked. That event invalidates the new unlock response, even though native opening succeeds. Further attempts repeat the false-locked cycle until a real lock or restart.

The actual App/API wrapper test in `late-receipt.test.tsx` still fails against the follow-up source, with `native remains active=true, unlocks=2, native locks=0`. `followup-late-receipt-results.json` records the failure. A separate actual Session/private-export probe pauses authorized publication, opens B, and then completes A. It confirms the old receipt while B remains active and the notification generated by another open. Results are in `followup-receipt-native.txt`.

Carry operation/session identity with receipts so an obsolete receipt cannot invalidate a newer session. If handling a receipt intentionally hides the current session, coordinate an actual native lock and the next opening. Preserve the old operation's secret-free completion acknowledgment. Do not turn this into a retryable unsaved error.
